# Addendum — Review 3: Fixing the two Phase 3–7 audit bugs

## Files changed
- `feature_store.py` — fixed a fallback-clamping bug (see "bug discovered" below).
- `scripts/build_pipeline.py` — forecast-generation loop rewritten to call `feature_store.get_context_row()` instead of duplicating feature-building logic; K-Means cluster interpretation rewritten to derive labels from actual per-cluster statistics instead of zone_type.
- `regenerate_forecasts_and_behaviour.py` (new, repo root) — one-off script that reruns *only* the two fixed sections against the **existing trained model** and **existing dataset** (no retraining, no dataset regeneration) and rewrites `forecasts` + `behaviour_patterns` in `pipeline_output.json`, leaving `model_evaluation`, `anomalies`, `recommendations`, `alerts`, `festival_forecasts`, and `meta` untouched.
- `backend/src/db/mysql_schema.sql` — added `is_fallback_date`, `fallback_reason` to `forecasts`; added `peak_hours`, `weekday_average`, `weekend_average`, `morning_peak_strength`, `evening_peak_strength`, `congestion_frequency`, `cluster_members_count` to `behaviour_patterns`.
- `backend/src/db/init_mysql.ts` — seed logic updated for the new columns; `applySchema()` made genuinely idempotent (previously `CREATE INDEX` without `IF NOT EXISTS` threw on every re-run against an already-initialized DB — caught and fixed during this session's verification).
- `backend/src/server.ts` — `/api/behaviour/patterns` now returns `cluster_id` plus every statistic backing the interpretation, not just the label.

## Forecast architecture: before → after
**Before:** `/predict_live` called `feature_store.get_context_row()`. The forecast-horizon loop inside `build_pipeline.py` (feeding `/api/traffic/forecast`, `/api/traffic/current`, `/api/traffic/heatmap`) built its own feature dict by hand, with weather/accident/construction hardcoded to "no effect" and lag/rolling approximated from a single "last row in the dataset."

**After:** both paths call the same `feature_store.get_context_row(zone_id, road_id, timestamp)`. One authoritative feature-generation function; `/predict_live` and the four horizon forecasts are guaranteed to resolve identical weather/festival/accident/construction/lag/rolling context for the same zone/road/timestamp.

**Bug discovered while fixing this:** the very first re-run produced only 68 of the expected 136 forecast rows (`next_1h`/`next_6h` failed for every road; `tomorrow`/`next_weekend` succeeded). Root cause: the simulation "today" (`sim_date = 2026-01-01`) is outside the dataset's 2025 window, so `feature_store`'s fallback substitutes the same month/day into 2025 — but the dataset actually starts `2025-01-02` (see Phase-3 finding on the New Year gap), so `2026-01-01 → 2025-01-01` is *itself* out of range. The existing fallback code's boundary-nudge subtracted a day in this case, walking the date **further** out of range instead of into it. Fixed: it now clamps to the correct boundary (`_year_min`/`_year_max`) while preserving the requested hour-of-day, and I re-verified all 136 rows generate correctly. This was a real bug in code from the previous session, caught only because I checked the row count rather than trusting a "no error thrown" result.

## Human behaviour architecture: before → after
**Before:** K-Means genuinely clustered 34 zone/weekday-weekend profiles into 7 clusters, but the human-readable label came from a separate `interpret_cluster_v2()` function keyed on `zone_type` + hour-window thresholds, ignoring the actual cluster ID. Proven broken via a cluster→label cross-tab (cluster 0 and cluster 2 both mapped to 3 different labels each).

**After:** for each of the 7 cluster IDs, `build_pipeline.py` now computes real aggregate statistics across every row KMeans assigned to it (average hourly profile, weekday/weekend averages and ratio, morning/evening peak strength, midday/nighttime activity, variability, and real congestion frequency pulled from `master`'s actual `congestion_level` column) and assigns exactly one interpretation per cluster from those statistics — zone_type is not consulted for the label. `MOBILITY_PROFILES` (unused dead code) was removed.

## Bugs discovered this session

2. Cluster-label/zone_type coupling (the one you asked me to fix) — confirmed and fixed.

## Remaining limitations
- The dataset's New Year gap (no `festival_day`/`day_before` phase for New Year, since the simulated year starts 2025-01-02) is unchanged — I was told not to regenerate the dataset, and confirmed in Phase 3 this doesn't affect any other festival. It does mean forecasts anchored close to the 2025/2026 boundary can coincidentally collide (see TEST B note above).
- `next_weekend`'s definition (`next Saturday from sim_date`) combined with year-substitution fallback does not guarantee the substituted date's actual day-of-week matches "Saturday" — this was already disclosed via `fallback_reason` before this session and remains disclosed; not something I could fix without inventing calendar data outside what exists.
- Cluster labels 0, 3, and 4 all independently resolved to "High Evening Activity Pattern" — that's a valid, non-forced outcome of the rule set (three distinct clusters can share a dominant characteristic while differing in exact magnitude/members), not a bug, but worth knowing the label set isn't guaranteed to produce 7 unique names.
